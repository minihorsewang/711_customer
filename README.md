### 架構決策：為什麼從原生 App 改成網頁版

討論後決定改走 **網頁版（未來可包裝成 PWA）**，原因：

1. **開發者沒有 Mac**：原生 iOS App 開發必須用 Xcode（僅 Mac 可跑），網頁版在 Windows 上就能完整開發與測試，不需額外買 Mac 或租雲端 Mac
2. **不需上架審核**：改版即時生效，不用等 App Store 審核
3. **跨平台**：同一份程式碼可以支援 iPhone、Android、電腦瀏覽器，原生方案只鎖 iPhone 會流失 Android 用戶
4. **這個 App 的核心功能本質上很「網頁化」**：表單填寫、格式驗證、匯出檔案、查資料庫，網頁技術棧完全能勝任
5. 之後如果真的要上架 App Store／Google Play 搶曝光，可以用 Capacitor 之類工具把網頁包裝成 App，是後補步驟，不影響現階段開發

## 二、產品定位與目標用戶

服務對象是**在台灣經營網路代購／小型電商（含直播賣家）的越南裔賣家**，他們透過 7-ELEVEN 交貨便（超商取貨付款 COD）出貨，但：

- 不熟中文，操作超商後台系統／Excel 建檔困難。
- 過去需要在電腦上手動製作 Excel 檔案再上傳 7-11 系統，流程繁瑣、易出錯。

核心價值：**用手機／網頁以越南語（或中文、英文）介面，快速產生符合 7-11 交貨便格式規範的訂單資料，降低操作門檻與出錯率。**

### 4.1 已實作的「7-11 門市查詢」規則

參考使用者提供的同類 App 操作影片（片中呈現官方 7-11 電子地圖查詢系統：可用「街道名稱／門市名稱／門市店號」三種方式查店），將原本讓賣家手動輸入 6 碼店號的欄位，改為：

- 點擊「在地圖上選擇」開啟門市查詢彈窗
- 可用「縣市下拉選單」＋「門市名稱／地址／店號關鍵字」即時篩選
- 選定門市後自動帶入店號、門市名稱、地址，並顯示綠色確認訊息
- **驗證規則**：店號必須來自查詢結果（比對 `stores.js` 資料庫），手動亂打的店號會被判定無效，避免上傳 7-11 系統時因店號輸入錯誤被退件
- 選定的門市名稱／地址會跟著訂單一起存進訂單列表、常用客戶、CSV 匯出內容

**目前限制**：`stores.js` 內的 16 筆門市是手動編寫的示範資料，**不是真實的全台 7-11 門市清單**。正式上線前必須換成真實資料源（見下方 4.2）。

### 4.2 前端技術（目前）
- 純 Vanilla JS + localStorage，無需 Node.js/建置流程，任何瀏覽器打開即可測試，這也是選擇網頁版後最直接受益的部分（Windows 環境零安裝門檻）
- 表單驗證規則集中在 `app.js` 的 `validateOrder()`，方便未來依 7-11 規則異動調整
- CSV 匯出符合 UTF-8 BOM，中文/越南文不會亂碼
- 可匯出 Excel `.xlsx`；此功能目前透過 CDN 載入 SheetJS，因此離線時可能無法使用
- 登入與註冊功能僅供原型展示，帳號及工作階段仍存於 localStorage，不可視為正式安全機制

### 4.3 尚未開發：正式後端與金流/物流串接

這是下一階段的核心工作，規劃如下：

#### (a) 串接綠界（ECPay）／藍新（NewebPay）物流 API
- 目的：讓賣家點「建立訂單」後**直接生成 7-11 交貨便的真實託運單**，而不只是匯出檔案
- 需要後端伺服器（不能在前端做，特店金鑰 HashKey/HashIV 絕不能曝露在瀏覽器）：
  ```
  賣家瀏覽器 → 你的後端 → 綠界/藍新物流 API → 回傳託運單號 + 可列印取貨單網址
  ```
- 物流 API 的「建立訂單」需要 `MerchantTradeNo`、`ReceiverName`、`ReceiverCellPhone`、`ReceiverStoreID`、`CollectionAmount` 等欄位，並用 `CheckMacValue` 簽章驗證
- 官方電子地圖串接後，門市查詢會改用綠界/藍新提供的真實地圖頁面，選店後由他們回傳真實店號給你的系統，取代目前 `stores.js` 的假資料

#### (b) 多租戶（多賣家共用平台）架構
因為會有多個直播賣家共用同一個網站，需要：
- **每個賣家用自己的 ECPay/藍新帳號**（而不是你自己申請一組帳號讓所有賣家共用），代收貨款才會直接進賣家自己的戶頭，你的平台單純做「工具」，不經手金流，法規風險最低
- 賣家登入系統（Email 或第三方登入）
- 資料庫要有 `seller_id` 貫穿所有資料表，確保賣家只能看到自己的訂單/客戶
- 每個賣家的 `HashKey`/`HashIV` 要加密儲存，這是高敏感資料

#### (c) 個資與隱私
- 買家姓名、電話、地址一旦集中存在你的資料庫，你就是個資控管者，需要：
  - 資料加密儲存、存取權限控管
  - 隱私權政策
  - 棄單黑名單功能的電話號碼建議雜湊處理，避免公開比對原始個資

## 五、商業模式建議

目前為工具型原型，尚未決定收費模式，建議路徑：

1. **Freemium 訂閱制**：免費版每日/每月建單筆數上限；付費版無限建單、雲端備份、真正串接物流直接建立託運單
2. **B2B 加值服務**：擴充支援全家、萊爾富等其他超商交貨便格式
3. **社群功能商業化**：棄單黑名單資料庫可作差異化賣點

## 七、風險與注意事項

- **金流/物流串接門檻**：綠界/藍新的「代收貨款」服務可能要求額外簽約或達一定業務規模才開放，需直接洽詢業務窗口確認資格
- **多租戶個資風險**：多個賣家的買家個資集中在同一平台，一旦外洩影響範圍是所有賣家的買家，需嚴謹的資安設計
- **依賴外部格式／API**：核心功能依賴 7-11 及金物流商的介面規則，對方調整規則需即時跟進
- **目前門市資料為假資料**：`stores.js` 僅供原型展示，正式上線前必須替換成真實門市清單（透過官方地圖 API 取得）

## 八、結論

專案已從「原生 iOS App」定調為「網頁版（可選 PWA 化）」，理由是開發環境限制（無 Mac）、跨平台需求與功能本質適合網頁技術。目前已完成一個功能完整的前端原型（三語言介面、建單驗證、7-11 門市查詢、客戶管理、棄單查詢、CSV 匯出），資料目前僅存在瀏覽器本機。下一步重點是**串接 ECPay/NewebPay 的真實物流 API**（取代示範門市資料、實現直接建立託運單）與**建立多租戶後端**（支援多個直播賣家獨立使用、資料互不干擾）。
